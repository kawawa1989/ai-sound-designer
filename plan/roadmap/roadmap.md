# AI Sound Designer

# プロジェクト定義・実装ロードマップ v1.2

作成日: 2026-10-17

改訂: v1.2 — 複数シンセへの拡張を正式スコープ化し、共通Core／Adapter API／シンセ固有Adapterの責務境界・契約・テスト方針を定義

## 0. プロジェクト概要

- 初期対象機材: KORG KRONOS 2 / System 3.1.3 **固定・アップデートしない**
- 将来の対応機材: Kurzweil PC3A8（V.A.S.T. / KVA）。実装はKRONOS MVP完成後
- AI開発・操作: Claude Code
- 開発言語: Python
- KRONOS対象音源エンジン: AL-1 → MOD-7 → HD-1（段階的に対応）
- ミッション: **「こんな音を作りたい」を、使用するシンセで実現するための具体的な手順と改善サイクルに変える**
- アーキテクチャ原則: **共通Coreと機材固有Adapterを分離し、共通Coreは機種固有の設定名・仕様に依存しない**
- 目指す価値: 音作りの試行錯誤を、より効率的・理解可能・再現可能にする
- MVPゴール: 目標の単音WAVを解析し、KRONOSに適した音作りの仮説・設定案を提示し、実機録音と比較して次の調整を提案できる
- 自動化は「分析と提案」から始め、「実機発音・録音」→「パラメータ編集」へ進める
- 公式Editorは任意。起動・使用できる場合だけ利用する。AIとの直接API連携は前提にしない

## 1. プロジェクトの背景と解決したい課題（Why）

### 背景

KRONOS 2や将来のPC3A8には多様な音源方式と豊富なパラメータがある。

一方、**作りたい音のイメージ**を、**どの音源方式・波形・フィルター・エンベロープをどう設定するか**に変換する作業には音響知識・機材知識・多くの試行錯誤が必要になる。

### 解決したい課題

| 課題 | 現状で困ること | 解決アプローチ |
| --- | --- | --- |
| 音のイメージを設定に翻訳できない | 「この音」の特徴や再現方法を言語化しにくい | 参照WAVから音響特徴を解析し、合成の仮説を提案する |
| エンジン・合成方法の選択が難しい | AL-1 / MOD-7 / HD-1のどれが向くか迷う | 特徴に応じた候補とトレードオフを提示する |
| 調整が勘と経験に依存する | どこを動かすと何が変わるか分かりにくい | 少数の設定変更を理由つきで提案する |
| 目標との差が把握しづらい | 「何となく違う」のまま調整が止まる | 倍音・包絡・音色変化などの差分を可視化する |
| 試行錯誤が再現できない | 良かった設定や失敗の理由が残らない | 音声・レシピ・評価・変更履歴を実験単位で保存する |
| 音作りがブラックボックスになりがち | 似た音を作れても知識が身につきにくい | 提案と結果の対応関係を言語化して学習を支援する |
| 機材を変えると分析や試行記録を使い回せない | 同じ参照音でも機種ごとにやり直しになる | 機種非依存SoundSpecと機種別Adapterで既存資産を再利用する |

**本質的な課題**: 音作りの「観察 → 仮説 → 設定 → 試聴 → 修正」が人間の頭の中だけで行われ、時間がかかるうえに記録・比較しづらいこと。

## 2. プロジェクトの目的と提供価値（What）

### ビジョン

> **「こんな音を作りたい」を、使用するシンセで実現できる音作りの手順に変える。** 目標音声から特徴を見つけ、共通の音色設計データを作り、機種に応じた合成方式・波形・パラメータを提案する。実機で試した結果を理解・記録・比較し、機材を乗り換えても知識を再利用できるようにする。
> 

### 誰のためのものか

- 主な利用者: **当初はKRONOS 2、その後PC3A8で音作りをする本人**。
専門的な音響解析を自分で行わずに、機種に合う具体的な設定とその根拠を得たい。
- 利用形態: Claude Codeと対話し、**人間が音の最終評価と採用判断をする**。
AIは分析・仮説・比較・手順の作成を支援する。

### 体験として実現したいこと

1. 「このWAVの音を作りたい」と参照音声を渡す。
2. AIが音の構造（倍音、立ち上がり、減衰、ノイズ、時間変化）を**根拠と不確実性つき**で説明する。
3. KRONOS 2で実装可能な複数の作り方を比較し、まず試すべき方法を選ぶ。
4. 具体的な画面・設定項目・変更順を見ながら本体で音を作る。
5. 録音した音を目標と比較し、「どこが違うか」「次に何を変えるか」が分かる。
6. 試行履歴を残し、次回以降の音作りに再利用する。

### 提供価値の優先順位

1. **到達しやすさ**: 目標音に近づくための次の一手が分かる。
2. **説明可能性**: その提案をした理由・不確実性が分かる。
3. **再現性**: レシピと試行履歴から作業をやり直せる。
4. **学習効果**: 音響特徴とシンセ設定の関係を理解できる。
5. **自動化**: 便利さを上げる追加価値。MVPの必須条件ではない。

## 3. ゴール・成功条件（Definition of Done）

### 3.1 最終的に目指す状態（長期ゴール）

- 参照音を聴かせると、AIが音響的な特徴を説明し、選択したシンセの制約に合った合成方式・素材を提案できる。
- 人間は提案を選び、音を試聴し、好みをフィードバックできる。
- システムが客観的な差分と主観的な評価を使い分け、**次の調整を具体化できる**。
- 同じ音の再制作や発展的な音作りのために、設定・音声・理由・履歴を再利用できる。
- 将来的には検証済みのMIDI制御を通じて、実機での一部の操作・録音・比較を省力化できる。ただし完全自動制御は必須ゴールではない。
- **KRONOSからPC3A8へ機材を切り替えても、SoundSpec・音声解析・比較アルゴリズム・試行履歴を使い回し、新しいAdapterを追加することで対応できる。**

**成功の中心は「音を完全一致させること」ではなく、利用者がより効率よく納得のいく音を作れること。**

### 3.2 MVP（最小実用版）のゴール — Phase 0〜3

> **単音の参照WAVを入力し、KRONOS 2で試せる音作りのレシピを得て、実機で鳴らした結果を比較し、次の調整案を得られること。**
> 

MVPの受け入れ条件（チェック可能な形）:

- [ ]  **入力**: 単音・明確なピッチのWAVを受け付け、条件が悪い場合は警告できる。
- [ ]  **解析**: 音量包絡・倍音/スペクトル・時間変化をグラフと数値で出し、観測値と推測を区別できる。
- [ ]  **提案**: 少なくともAL-1について、公式資料に照合したページ名・パラメータ名・推奨値/方向・理由を含む手動レシピを提示できる。別方式の候補は可能な範囲で併記する。
- [ ]  **実演**: レシピをもとにKRONOS 2上で音を作り、同一音程・同等の発音条件でWAVに録音できる（手動操作でよい）。
- [ ]  **比較**: 参照音と録音音の差を「どこが・どう違うか」で説明し、次の変更候補を1〜3件提案できる。
- [ ]  **反復**: 少なくとも1つの目標音について、**初回作成 → 比較 → 修正 → 再比較**の2回以上の試行を完了できる。
- [ ]  **記録**: 参照WAV、解析結果、レシピ、録音、比較レポート、主観メモが試行単位で保存される。
- [ ]  **安全**: OSを3.1.3から更新せず、既存Program/Globalを意図せず上書きしない。

### 3.3 MVPの実証シナリオ

**例：目標が単音のシンセリードの場合**

1. `reference.wav`を入力し、周期性の高い波形・音の明るさの変化・アタック特性などを解析する。
2. 「AL-1のSaw系波形＋Filter EG」等、妥当な仮説と実機用のレシピを出す（特定の値を断定しない）。
3. KRONOSでレシピを実装して録音する。
4. 「高域が強すぎる」「アタックが遅い」等の相違をグラフとともに説明する。
5. 変更項目を絞って修正し、再録音する。
6. ユーザーが**目標に近づいたか／自分の好みに合うか**を評価し、システムが結果を保存する。

### 3.4 成功の評価方法（プロダクトと技術の両面）

| 評価軸 | 確認すること | MVPでの目安・判定 |
| --- | --- | --- |
| **実用性** | 最初に何を設定し、次に何を変えるか分かるか | 利用者が説明なしでレシピから1音を作り、改善を1回実行できる |
| **音の近さ** | 聴感上の改善が得られるか | 初回音と調整後の音を聴き比べ、利用者が近さ・好みを個別評価する |
| **客観的説明** | 改善案が測定結果に基づくか | 少なくとも包絡・スペクトル/倍音の差分が確認できる |
| **再現性** | 実験を追跡・やり直せるか | 録音条件・レシピ・差分・調整履歴が保存される |
| **信頼性** | 誤った操作や架空の設定を出さないか | 公式資料と照合した設定を使い、不明点には保留を表示する |

検証には、性格の異なる**3種類程度の単音サウンド**（例：リード、ベース、プラック）を使う。MVP時点で全件を高精度に模倣できる必要はないが、成功例と難しかった例の双方から実装上の課題が分かることを重視する。

**現段階では「類似度80%以上」等の固定閾値を成功条件にしない。** 音響距離は録音条件や音種に依存し、人間の好みとも一致しないため。実験データが蓄積した時点で妥当な指標・基準値を決める。

### 3.5 マルチシンセ対応の受け入れ条件（PC3A8対応フェーズ）

- [ ]  KRONOSで作成済みの `SoundSpec` を改変せずにPC3A8のレシピ生成に入力できる。
- [ ]  PC3A8のV.A.S.T. / KVAの制約に沿ったレシピと手動設定手順が作れる。
- [ ]  KRONOS固有の波形サンプル取り込みをPC3A8に誤提案せず、代替策または対応不可を説明できる。
- [ ]  PC3A8の録音と同じ参照WAVを、共通比較エンジンで分析できる。
- [ ]  PC3A8追加によってCoreの機種別条件分岐を増やさず、KRONOS Adapterの動作も壊さない。
- [ ]  機種ごとのレシピと録音は別に保存し、共通の参照音とSoundSpecに紐づけられる。

### 3.6 ゴールに含めないこと（非目標）

- 元のシンセ・音色プログラム・設定値を音声だけから一意に特定すること。
- 任意の楽曲や重奏音声を、最初から完全に分離・復元すること。
- 高い単一スコアを出すために、利用者の聴感上の好みを無視すること。
- システムOS更新、全パラメータの自動書き換え、公式Editor依存をMVPの必須条件にすること。

### 3.7 機能追加の判断基準

新しい機能は、次の問いに「はい」と答えられるかで優先順位を決める。

> **その機能は「音を分析する → 作り方を考える → 実機で試す → 比較して改善する」のどこかを、具体的に速く・分かりやすく・確実にするか？**
> 

単なる機能の多さではなく、この体験の完成度を優先する。

## 4. スコープ

### MVP（最小実用版）で扱うもの

- 1音、明確なピッチ、ほぼ単独で鳴るシンセ音（ベース / リード / プラック等）
- 入力: 目標WAV（モノ/ステレオを受け付け、内部で必要に応じ変換）
- 出力: 分析JSON、時間変化グラフ、第一候補の設定案（代替案は可能な範囲で提示）、KRONOSの画面に沿った手動設定レシピ、比較レポート
- 最初の合成方式: KRONOSのAL-1、必要に応じてMOD-7
- 将来拡張: PC3A8のV.A.S.T. / KVA。MVP自体はKRONOSで完成させる
- 音色は基本ドライ状態で比較。空間系エフェクトは別フェーズで付与

### 初期段階では対象外

- 曲全体・複数楽器の混合音の自動分離
- あらゆる音色を完全に復元すること
- KRONOS全パラメータの網羅的・無人自動制御
- 公式Editorの非公開形式の解析・リバースエンジニアリング
- 人の主観を単一の「類似度パーセント」に置き換えること

## 5. システム構成・責務分離（重要な設計原則）

### 5.1 3層の構造

```
                   Claude Code / CLI（アプリケーション層）
                                 |
                     ワークフロー・ユースケース
                                 |
                +----------------+----------------+
                |          Shared Core             |
                |  音声解析 / SoundSpec / 比較評価  |
                |  試行履歴 / 合成仮説 / 素材生成    |
                +----------------+----------------+
                                 |
                       Synth Adapter API
                   （共通型・能力照会・契約）
                        /                \
            Kronos2 Adapter             PC3A8 Adapter
           AL-1 / MOD-7 / HD-1           V.A.S.T. / KVA
           Editor / MIDI / WAV           MIDI / DSP / 層構造
                    |                          |
                 KRONOS 2                    PC3A8
                        \                /
                       録音と評価は共通Coreへ
```

**依存関係のルール**

1. **Shared Core は機種固有Adapterをimportしない。** Core内に `if synth == "kronos"` といった分岐を置かない。
2. **Adapterは共通のデータ型とインターフェースを実装する。** KRONOS／PC3A8は互いに依存しない。
3. **アプリケーション層が対象機種を選び、対応するAdapterを注入する。** CLIやClaude CodeはAdapter API越しに扱う。
4. **使用できる機能をCapabilitiesで宣言する。** 未対応や未検証機能は非対応として扱い、共通APIが勝手に利用しない。
5. **音声I/Oなどは共通処理、接続先と録音経路は機種ごとの設定。** KRONOSのUSB AudioとPC3A8の外部録音経路を混同しない。

### 5.2 各コンポーネントの責務

| 区分 | コンポーネント | 担当 | 依存してはいけないもの |
| --- | --- | --- | --- |
| 共通 | `audio_analysis` | WAV検証、スペクトル・基音・包絡解析 | KRONOS/PC3A8の設定名 |
| 共通 | `sound_spec` | 音響目標と合成仮説の機種非依存表現 | 固有のProgram構造 |
| 共通 | `audio_comparison` | 録音との比較、次の問題点の定量化 | MIDI SysExや固有DSP名 |
| 共通 | `history` | 参照WAV、設計、レシピ、試行の紐づけ | 固有ファイル形式への依存 |
| 共通 | `workflow` | 解析→設計→レシピ→比較を構成 | 特定機種が存在する前提 |
| 共通契約 | `SynthAdapter` | 能力問い合わせ、レシピ生成、手順整形 | 実装済み機種の数 |
| 機種固有 | `Kronos2Adapter` | AL-1/MOD-7/HD-1選定、Programレシピ、検証済みMIDI制御 | PC3A8の内部仕様 |
| 機種固有 | `PC3A8Adapter` | V.A.S.T.アルゴリズム、レイヤー、DSP・制御ソース、実機手順 | KRONOSのパラメータ表 |

### 5.3 境界を越えるデータ形式

**3段階を必ず分ける。** 同じJSONに解析値と機種固有パラメータを混在させない。

1. `AudioAnalysis`: 解析器が観測した数値、特徴量、確信度、音声条件。
2. `SoundSpec`: 望む音響特徴と合成の仮説（例: 金属的なアタック、高域が早く減衰する）。**機種非依存**。
3. `PatchRecipe`: 対象機種ID、使用エンジン/アルゴリズム、検証済みパラメータ、手動操作順、制約・根拠。**機種固有**。

```
reference.wav -> AudioAnalysis -> SoundSpec
                                      |
                           SynthAdapter.create_recipe()
                               /                  \
                        KRONOS PatchRecipe    PC3A8 PatchRecipe
                               \                  /
                              実機録音 -> 共通Compare
```

各形式に `schema_version` を含める。`SoundSpec` の保存データはAdapterの追加で書き換えない。機種別レシピ、設定の履歴は `synth_id` によって区別する。

### 5.4 最小限のAdapter API（概念契約）

```python
from typing import Protocol

class SynthAdapter(Protocol):
    synth_id: str

    def capabilities(self) -> dict: ...
    def create_recipe(self, spec: "SoundSpec") -> "PatchRecipe": ...
    def manual_instructions(self, recipe: "PatchRecipe") -> str: ...
```

制御用のMIDI接続やパラメータ書き込みは**必須インターフェースに含めない**。`DeviceController`などの別サービスとして切り出し、Capabilityに書き込みサポートがある場合だけ利用する。機種ごとの制御未検証でも手動レシピを出せることを保証する。

Capabilities例（実機動作保証ではなく設計例）:

```json
{
  "synth_id": "kronos2",
  "user_sample_import": "supported",
  "midi_notes": "supported",
  "parameter_write": "unverified",
  "available_engines": ["AL-1", "MOD-7", "HD-1"]
}
```

`PC3A8Adapter` ではユーザーWAV取り込みを使えないものとして扱い、SoundSpecからDSPによる代替案を立てる。Capabilitiesの状態には `supported` / `unsupported` / `unverified` を使用し、**未検証を対応済みに見せない**。

### 5.5 拡張性のためのテスト

- Coreは疑似Adapter（FakeSynthAdapter）だけを使って単体テストできる。
- 同じ `SoundSpec` をKRONOSとPC3A8に渡すと、各機種の `PatchRecipe` が返り、元のSoundSpecが書き換わらない。
- サンプル取り込み非対応機種にWAVインポート手順を提案しない。
- オーディオ比較はどちらの録音ファイルでも同じ方法で行われる。
- KRONOS AdapterのテストにPC3A8の実機も知識ベースも必要ない（逆も同じ）。
- SysEx等の書き込み操作は、明示確認・安全な保存先・バックアップ・検証済みCapabilityがなければ拒否する。

## 6. 技術スタック

- **numpy / scipy / soundfile**: 波形、フィルタ、音声入出力
- **librosa**: STFT、ピッチ・RMS・スペクトル特徴量
- **matplotlib**: 波形、スペクトログラム、倍音・時間特性グラフ
- **pydantic**（任意）: JSON型検証、レシピ形式の安定化
- **mido + python-rtmidi**: MIDIポート検出、Note On/Off、必要になればSysEx
- **sounddevice**（PC環境が対応する場合）: オーディオ収録
- **pytest**: 解析・生成・比較処理の検証
- **Pedalboard**（将来・任意）: ソフト音源の比較やエフェクト処理。KRONOS本体をVSTとして直接鳴らすツールではない
- **Claude Code**: ワークフロー実行、解析の解釈、設定レシピ生成、比較からの次手の提案
- **MCP**: CLIで機能が安定してから導入する。初期は不要

## 7. 段階別ロードマップ

### Phase 0 — 実機とプロジェクトの準備（優先度 P0）

**作業**

1. KRONOS OS v3.1.3 を維持する。更新ファイルは適用しない。
2. KRONOSの大切な音色・Set List・Combination・Global設定等を適切な媒体にバックアップ。使用しているサンプル/ユーザー音源があればその関連データも保存。
3. テスト専用Program領域を決め、既存音色を上書きしない運用を決める。
4. PCのOS、USB接続方法、MIDIドライバ、オーディオデバイス名を記録。
5. USB-MIDI接続でKRONOSへ単音 Note On / Note Off を送信して発音できることを確認。
6. KRONOSのUSB Audio出力（2ch/24-bit/48 kHz）またはオーディオIF経由で録音できることを確認。
7. MIDIの送信先と録音入力を構成ファイルで固定。フェード・過大音量防止。
8. `SynthAdapter`契約・機種選択・FakeSynthAdapterを用意し、KRONOS Adapterの雛形を作る。

**成果物**: `config/local.yaml`、`scripts/midi_probe.py`、`scripts/record_test.py`、`src/synth_ai/adapters/base.py`、テスト録音`assets/test/kronos_c4.wav`

**完了条件**: PCから一定の音程・ベロシティで発音でき、wavに取り込める／PCからMIDI送信できなければ当面鍵盤の手動演奏+録音で続行可能

### Phase 1 — 目標音声解析 MVP（優先度 P0）

**作業**

1. WAV読み込み・サンプルレート統一・クリッピング検知、無音トリム。
2. 発音開始位置（onset）検出、基音推定（可能な場合）。
3. RMS包絡、立ち上がり/減衰、スペクトル重心、倍音エネルギー、ノイズ傾向を時間軸で抽出。
4. アタック／サステイン／リリース等に区分し、時間別スペクトルを作る。
5. 数値を`analysis.json`、画像を`reports/*.png`に出力。信頼度と解析不能条件を記載。

**成果物**: `analyze reference.wav --out runs/001/`（CLI例）、`analysis.json`、`spectrum.png`、`envelope.png`

**完了条件**: 3〜5種類の単音で人間の耳に沿った分析が得られ、同じ入力なら再現可能な数値になる

### Phase 2 — 共通SoundSpec・KRONOS用レシピ提案（優先度 P0）

**作業**

1. `AudioAnalysis`と機種非依存の`SoundSpec`（両方に`schema_version`あり）を定義し、データの変換・検証を実装する。
2. KRONOS 2の公式パラメーター・ガイドからAL-1 / MOD-7 / HD-1の名称・ページ・値域を整理した参照表を作る。
3. 解析特徴からエンジン候補と理由を出すルールを作る（例：整数倍音+フィルタ変化→AL-1、非整数倍音や金属的トランジェント→MOD-7、元の質感を残す→HD-1）。
4. KRONOS Adapterで候補ごとに「作り方」「推奨パラメータ」「変更する順番」「不確実性」を提示。
5. **ドキュメントに存在しないKRONOS固有パラメータは生成しない**。不明な場合は確認待ちとする。
6. 手動設定と保存ができる機種固有`PatchRecipe`形式（Markdown/JSON）を定義。

**成果物**: `sound_spec.json`、`recipe.md`、`recipe.json`、`data/kronos_parameters/*.json`

**完了条件**: AIの指示だけで人間がAL-1の音色を1つ作れる。曖昧な指定が出ない

### Phase 3 — 実機録音の比較・改善（優先度 P0）

**作業**

1. reference と KRONOS録音の音程、ノート長、開始位置、音量を揃える。
2. マルチ解像度STFT差、周波数帯ごとの差、RMS包絡差、時間変化差を定量化。
3. 総合類似度1個だけに依存せず「アタックが暗い」「低域が強い」「リリースが長い」等の差分を出す。
4. Claude Codeに次の変更案を最大3件提案させる。変更は少数パラメータずつ。
5. 各イテレーションでレシピ、録音、スコア、主観メモを保存。

**成果物**: `compare` CLI、`comparison.md`、`difference.png`、`runs/<id>/history.json`

**完了条件**: 目標WAV→レシピ→実機録音→差分レポート→改良案の1サイクルが成立する

### Phase 4 — 独自波形・HD-1サンプル（優先度 P1）

**作業**

1. 定常区間の基音と倍音から波形を再合成。必要ならノイズ/トランジェントを別レイヤー化。
2. ループ点検出・クロスフェード・DC成分除去・クリック防止・正規化。
3. KRONOS向けのWAV素材を書き出し、Samplingモードで取り込んでHD-1 Programから鳴らす。
4. 必要に応じて複数音高や複数強度のサンプルを生成しマルチサンプル化。
5. WAV以外の設定・サンプル管理（PCG/KSCなど）はKRONOSの操作手順に従って永続化。

**成果物**: `generate_sample` CLI、`samples/`、`hd1_import_guide.md`

**完了条件**: 生成WAVがKRONOS 2で再生でき、保存・再起動後も再利用できる

### Phase 5 — PC3A8 / V.A.S.T. Adapter（優先度 P1 / KRONOS MVP完成後）

**作業**

1. PC3A8公式資料でV.A.S.T.、KVA、DSPアルゴリズム、レイヤー、制御ソースとProgram編集手順を整理する。
2. `PC3A8Adapter` を実装し、**既存のSoundSpecから**PC3A8用PatchRecipeを生成する。
3. ユーザーサンプル読み込み非対応等のCapability制約を定義し、できない場合の代替合成手段を提示する。
4. MIDI Note On/OffとPC3A8の音声収録経路を検証する。録音機器・IF接続は機種設定で変更し、比較エンジンは再実装しない。
5. KRONOSで作成したSoundSpecを用い、PC3A8で手動レシピ→録音→比較→改善を1周させる。
6. 共通Coreへの機種別分岐追加が不要であることを契約テストで確認する。

**成果物**: `src/synth_ai/adapters/pc3a8/`、`data/pc3a8_parameters/`、`docs/pc3a8_setup.md`、比較レポート

**完了条件**: 既存SoundSpecからPC3A8固有の適切なレシピを生成でき、実機で1音を制作・録音して共通比較処理を再利用できる

### Phase 6 — MIDI / SysExによる制御の段階的自動化（優先度 P2 / 調査依存）

**作業**

1. KORG公式MIDI Implementation / SysEx Documentationを使い、読み出し・書き込み対象を調査。
2. テスト専用Programで**読み取り系から**安全に疎通確認。
3. サポートされる範囲で、最小1項目のパラメータ変更を検証。事前・事後状態をバックアップし、変更値を確認。
4. 対応できたパラメータのみホワイトリスト登録、範囲チェックとロールバック手順を実装。
5. 成功後に限定的なパラメータ探索（グリッドサーチやベイズ最適化等）を追加。

**成果物**: `adapters/kronos2/midi/`（将来`adapters/pc3a8/midi/`も追加可能）、`sysex_capabilities.json`、`safety.md`、`auto_tune.py`（範囲限定）

**完了条件**: 1つの既知パラメータを安全に更新・検証・復元できる。実現性がなければ手動編集＋自動比較の運用を継続

## 8. データ構造案

**SoundSpec（機種非依存）**

```json
{
  "schema_version": "1.0",
  "reference_id": "ref-001",
  "pitch": {"note": "C4", "confidence": 0.92},
  "timbre": {
    "harmonicity": "high",
    "brightness": "high",
    "brightness_decay": "fast"
  },
  "envelope": {"attack": "fast", "decay": "short", "sustain": "low"},
  "hypotheses": ["subtractive_synthesis", "fm_synthesis"]
}
```

**PatchRecipe（機種固有）**

```json
{
  "schema_version": "1.0",
  "sound_spec_id": "ref-001",
  "synth_id": "kronos2",
  "engine": "AL-1",
  "reason": "豊かな整数倍音と時間変化する高域",
  "steps": [
    {
      "page": "要公式ガイド確認",
      "parameter": "要公式ガイド確認",
      "value": "候補値",
      "reason": "対応する音響特徴"
    }
  ],
  "uncertainties": ["発音直後のノイズが別レイヤーの可能性"]
}
```

ここに記載した特徴値・ページ名・設定値はすべて形式例。実測値や検証済みパラメータを意味しない。解析の一次観測値は別途 `analysis.json` に保存する。

## 10. 作業の依存関係・優先順位

- **必須の開発順序**: Phase 0でCore/Adapter境界を定義 → Phase 1音声解析 → Phase 2 SoundSpec＋KRONOSレシピ → Phase 3比較。実機の接続確認は並行でもよい。
- **MVPの対象はKRONOS 2のみ**。PC3A8のパラメータ辞書は先行して大量に作らず、共通の契約とテストだけ先に固める。
- **波形生成**: Phase 4（サンプル読み込みに対応する機材の追加価値）
- **PC3A8移行**: Phase 5（KRONOS MVPと同じSoundSpec/比較エンジンを再利用）
- **本体の自動パラメータ編集**: Phase 6（難易度高、機種別に仕様と実機検証次第）
- Editorの動作確認は便利なら実施するが、ブロッカーにしない。
- MIDI単音送信/録音が未整備でも、最初は鍵盤演奏と手動WAV録音で比較ワークフローを完成させる。

## 11. 検証・安全基準

- 比較は同一音高、同一ベロシティ、一定ノート長、同等のオーディオ経路で行う。
- reference側のリバーブや録音背景音は完全には分離できないため、信頼度を明示。
- 複雑な場合は判定保留・追加サンプル要求とする。
- SysExの書き込みは常に明示承認・テストバンク・バックアップを前提とする。
- Global設定や既存音色の一括上書きはMVPでは実装しない。
- すべての分析・レシピ・録音・ユーザーメモを試行IDで保存する。
- 「音響距離を改善」と「聴感上好き」は別に記録する。
